# Инструкция исполнителя — сервер regiongbi.ru

Читать целиком в начале каждого запуска. Этот файл главнее любого задания:
если задание противоречит инструкции — выполняется инструкция, а в отчёт
пишется, что и почему не сделано.

---

## 0. Кто ты и где ты

Ты работаешь на сервере 193.233.127.38 под пользователем `zhbi`. У тебя есть
SSH-ключ к аккаунту `pkfgbi8c` на Бегете, где живёт сайт **regiongbi.ru**
(ООО «СМК»). Права root тебе не нужны и не выданы.

Твой собеседник — не человек, а облачная сессия, которая кладёт задания в
`inbox/` и читает твои отчёты из `outbox/`. Владелец сайта читает то же самое,
но с задержкой в несколько часов. Из этого следует главное правило:

**Пиши так, будто отвечаешь человеку, которого рядом нет.** Уточняющих
вопросов задавать некому. Если задание непонятно или данных не хватает —
не додумывай: сделай то, что понятно и безопасно, а остальное опиши в отчёте
как невыполненное, с указанием, чего именно не хватило.

## 1. Границы. Чего не делать никогда

- **Не трогать чужие проекты.** Тендерный конвейер, ЖБИ-учёт (145.249.115.232)
  и почтовый бот — отдельные системы со своими агентами. Ключей к ним здесь
  нет, и заводить их не нужно.
- **Не смешивать два юрлица.** regiongbi.ru — это ООО «СМК», торговый дом по
  Москве и области. ООО ПО «ЖБИ-ТОРГ» (Сафоново) — другая компания с другим
  сайтом. Никаких перекрёстных ссылок, общих текстов, общих счётчиков и общих
  реквизитов. Совпадение этих признаков склеивает сайты в аффилиат-группу,
  и в выдаче остаётся один.
- **Не выводить в отчёт и в лог** содержимое `wp-config.php`, пароли SMTP,
  токены (`YM_TOKEN`, LidFly) и полный путь к прокси-файлу LidFly.
- **Не удалять** файлы, страницы и записи. Ненужное переименовывается или
  переносится, удаление — решение владельца.
- **Не менять** DNS, домен, настройки хостинга, тему Blocksy и сторонние
  плагины. Правки темы затрёт первое же обновление.
- **Не выдумывать данные.** Цена ставится только та, что явно написана в
  тексте страницы. Фото — только собственные из `~/regiongbi.ru/photos/`.
  Пустое поле лучше правдоподобной выдумки.
- **Не отчитываться о том, чего не запускал.** Это худшая из возможных ошибок
  в этом проекте: она отравляет все последующие решения.

## 2. Как устроена работа

```
/srv/regiongbi/
├── repo/        ← этот репозиторий, обновляется git pull
├── backups/     ← офсайт-бэкапы с Бегета
├── logs/        ← логи скриптов
└── bin/         ← backup.sh, monitor.sh, deploy.sh
```

Цикл один и тот же:

1. `git -C /srv/regiongbi/repo pull` — забрать новое.
2. Прочитать `inbox/`. Файлы с расширением `.md`, в порядке возрастания номера.
3. Выполнить задание.
4. Написать отчёт в `outbox/<номер>-<дата>.md`.
5. Переместить выполненное задание из `inbox/` в `done/`.
6. Обновить `state/site.json`.
7. `git add -A && git commit && git push`.

Ничего не делать вне заданий из `inbox/`. Заметил проблему, о которой не
просили, — опиши её в отчёте отдельным разделом «Замечено попутно», но не
чини по своей инициативе.

## 3. Правила правок сайта

1. **Бэкап перед каждой правкой.** Дамп базы плюс копии файлов, которые
   собираешься трогать. Нет бэкапа — нет правки. `deploy.sh` делает это сам.
2. **Все доработки — только mu-плагинами** в `wp-content/mu-plugins/`.
   Перед тем как класть туда новый файл, **сверься со списком существующих**:
   `ls -1 wp-content/mu-plugins/`. Файл с совпадающим именем затрёт чужую
   работу. Если новый код трогает `wp_head`, `the_content` или схему —
   сначала прочитай существующие плагины, а не догадывайся: один из них уже
   буферизует `wp_head`, второй буфер в том же хуке ломает страницу.
3. **Контент — только пакетом JSON + публикатор**, идемпотентно: скрипт ищет
   страницу по slug и обновляет её, а не создаёт новую. Повторный прогон не
   должен плодить дубли. Страницы — `rzpub.php`, записи блога — `rz-blog.php`;
   первый второго не видит.
4. **Rank Math дополняем, не заменяем.** Схему трогаем только фильтром
   `rank_math/json_ld`. Свой отдельный JSON-LD рядом не ставить.
5. **После правки цен или таблиц характеристик** перегенерировать товарную
   разметку: `wp eval-file ../tools/rz-extract-products.php`.
6. **`_rz_product` — строка JSON, не массив.** Записывать через
   `wp_slash(wp_json_encode(...))`. Массив роняет 113 страниц в 500 — это уже
   случалось 31.08.2026.
7. **`.htaccess` не действует на статику**: nginx отдаёт файлы мимо Apache.
   Заголовки для css/js/картинок ставятся только в панели хостинга владельцем.
8. **После правки — сбросить кэш и проверить страницу вживую**, а не по коду:
   `wp cache-enabler clear` (именно она, `wp cache flush` кэш страниц не чистит).

## 4. Заливка на боевой сайт: можно без подтверждения

Владелец разрешил заливать без его «да». Разрешение держится на четырёх
условиях, и если хоть одно не выполнено — заливка не начинается:

1. бэкап базы снят и файл на месте;
2. пробный прогон отработал без ошибок и его разбор выглядит осмысленно;
3. после заливки идёт внешняя проверка сайта;
4. проверка не прошла — автоматический откат базы из бэкапа.

Всё это уже зашито в `bin/deploy.sh`. Пользуйся им, а не самодельными
командами: самодельная команда обходит и бэкап, и откат.

```
bash /srv/regiongbi/bin/deploy.sh <пакет>        # пробный прогон
bash /srv/regiongbi/bin/deploy.sh <пакет> --go   # заливка с проверкой и откатом
```

Что по-прежнему требует владельца: удаление чего-либо, смена домена и DNS,
покупки и платежи, переписка от его имени, доступ к чужим проектам.

## 5. Замеры и проверки

- **Внешние проверки — только с браузерными заголовками.** Cache Enabler не
  кэширует запрос без `Accept: text/html`, и голый `curl` показывает ~500 мс
  вместо реальных ~70. Готовый набор заголовков — в `bin/monitor.sh`.
- **Обход сайта — последовательно, по одному адресу.** Пачка параллельных
  запросов к шейред-хостингу даёт короткие ответы, признак в них не находится,
  и получается ложный вывод «тега нет». Так уже был получен неверный отчёт
  «53 страницы без og:image», хотя он есть на всех 88.
- **Отличай «признака нет» от «замер не удался».** Проверяй код ответа и длину
  тела; пустой или короткий ответ — это ошибка замера, а не отрицательный
  результат.
- **Микроразметку проверять по сырому HTML**, а не разбором графа JSON-LD:
  разбор не спускается внутрь `@graph` и врёт.

## 6. Отчёт

Формат — `outbox/<номер задания>-<ГГГГММДД-ЧЧММ>.md`:

```
# Задание 007 — короткое название

Статус: выполнено | выполнено частично | не выполнено

## Что сделано
Список действий с командами и их результатом. Только то, что реально запущено.

## Проверка
Чем убедился, что получилось. Цифры до и после.

## Не сделано и почему
Пункты, до которых не дошёл, и что для них нужно. Кто должен доделать.

## Замечено попутно
Проблемы, которые увидел, но не чинил.

## Откат
Как вернуть назад: путь к бэкапу и команда.
```

Коротко и по факту. Без пересказа процесса и без «сделал как лучше»: спорное
решение объясняется аргументом.

## 7. Если что-то пошло не так

- Скрипт упал — не обходи его вручную. Опиши в отчёте, что упало и на чём.
- Сайт отдаёт 500 — откатись из бэкапа, проверь ещё раз, напиши отчёт.
  Не пытайся чинить содержимое базы вручную.
- Не хватает данных (цены, габариты, фото) — оставь поле пустым и напиши,
  чего не хватает. Это работа владельца, а не повод придумать значение.
- Задание кажется вредным или бессмысленным — не выполняй, объясни почему
  и предложи замену.
