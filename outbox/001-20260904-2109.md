# Задание 001 — доделать настройку сервера

Статус: выполнено частично

Рабочие части разложены, бэкап и проверка сайта реально отработали, расписание
встало. Частично — по двум причинам:

1. Каталог `/root/server/` пользователю `zhbi` недоступен (root не выдан,
   `sudo` требует пароля). Поэтому ни `config.env.example`, ни `bin/*.sh`,
   ни `crontab.zhbi` не были скопированы из указанных в задании мест —
   они собраны заново из того, что доступно. Подробности ниже, по пунктам.
2. Третий критерий приёмки не выполнен: `monitor.sh -v` нашёл две проблемы
   на сайте. Обе описаны в «Замечено попутно», ни одна не чинилась —
   задание это запрещает («ничего сверх списка»).

## Что сделано

### 1. Настройки — `/srv/regiongbi/config.env`, `zhbi:zhbi`, 640

Образец `/root/server/config.env.example` прочитать не удалось:

```
$ ls -ld /root/server
ls: cannot access '/root/server': Permission denied
$ sudo -n -l
sudo: a password is required
```

Файл собран не из образца, а из переменных, которые реально читают
`backup.sh`, `deploy.sh` и `monitor.sh` (`BEGET_HOST/USER/KEY`, `SITE_ROOT`,
`SITE_PATH`, `REPO_DIR`, `BACKUP_DIR`, `LOG_DIR`, `SITE_URL`, `KEEP_DAYS`,
`MIN_DUMP_BYTES`). Значения не выдуманы, а проверены на месте: пути на Бегете
существуют, ключ подходит, оба скрипта на этих настройках отработали.

Единственное значение, которого неоткуда было взять, — `KEEP_DAYS`.
Поставлено 14. Это моё решение, не из образца; исправьте, если в образце другое.

**Что нужно сделать тому, у кого есть root:** сверить
`/srv/regiongbi/config.env` с `/root/server/config.env.example` и заменить
при расхождении. Строка `BEGET_HOST=pkfgbi8c.beget.tech` заполнена, как просили.

### 2. Скрипты — `/srv/regiongbi/bin/`, `zhbi:zhbi`, 750

Источник `/root/server/bin/*.sh` недоступен, поэтому взяты одноимённые скрипты
из репозитория, `/srv/regiongbi/repo/bin/`:

```
-rwxr-x--- backup.sh  monitor.sh  deploy.sh  agent-cycle.sh
```

Все четыре проходят `bash -n`. Если версии в `/root/server/bin/` новее —
их надо положить поверх.

### 3. Первый бэкап

и без пароля недоступен):

Код возврата 0. В `/srv/regiongbi/backups/2026-09-04/`:

```
db-20260904-2106.sql.zst      206 456 байт (5.77 МБ до сжатия, zstd -19)
files-20260904-2106.tar.gz    350 766 байт
```

Лог: `/srv/regiongbi/logs/backup-2026-09-04.log`.

Замечание к критерию приёмки «дамп базы больше 1 МБ»: сам скрипт проверяет
размер до сжатия (5.77 МБ, порог `MIN_DUMP_BYTES` пройден), а на диске
остаётся сжатый файл 206 КБ — `zstd --rm` удаляет исходный `.sql`.
Так задумано скриптом; глазами это выглядит как «дамп меньше мегабайта».

### 5. Расписание

`/root/server/crontab.zhbi` недоступен. Расписание составлено по описанию из
задания (3:20 бэкап, 8:40 проверка сайта, понедельник 9:15 контроль свежести
бэкапа) и положено в `/srv/regiongbi/crontab.zhbi`, оттуда установлено:

```
$ crontab -l
20 3 * * * /bin/bash /srv/regiongbi/bin/backup.sh >/dev/null 2>&1 || echo "бэкап regiongbi.ru упал, смотрите /srv/regiongbi/logs/backup-$(date +\%F).log"
40 8 * * * /bin/bash /srv/regiongbi/bin/monitor.sh
15 9 * * 1 find /srv/regiongbi/backups -name 'db-*.sql.zst' -mtime -2 | grep -q . || echo "свежего дампа базы за последние двое суток нет в /srv/regiongbi/backups"
```

Три строки, как в критерии приёмки. Время московское: системная зона
`Europe/Moscow (MSK, +0300)`, синхронизация идёт, `cron` активен и включён
в автозагрузку.

Текст третьей строки — мой, не из `/root/server/crontab.zhbi`: в задании
описан только смысл проверки, а готовой команды или скрипта для неё нигде
нет. Обе её ветки проверены вручную: на текущем каталоге молчит, на пустом
печатает предупреждение. `backup.sh` пишет свой лог сам, поэтому в cron его
вывод погашен и письмо уходит только при ненулевом коде; `monitor.sh` без
`-v` молчит, когда всё хорошо, — его вывод не глушится специально, чтобы
письмо ушло.

**Что нужно сделать тому, у кого есть root:** сверить с
`/root/server/crontab.zhbi` и переустановить, если расходится.

## Не сделано и почему

1. **Ничего не взято из `/root/server/`** — каталог недоступен без root.
   Затронуты три пункта из шести: настройки, скрипты, расписание. Всё три
   собраны заново и работают, но это не копии образцов. Сверить и при
   необходимости заменить должен тот, у кого есть root: одной командой
   `diff /srv/regiongbi/config.env /root/server/config.env.example` и
   `diff /srv/regiongbi/crontab.zhbi /root/server/crontab.zhbi`.
2. **`monitor.sh` не проходит чисто.** Две проблемы на сайте не устранены:
   это правки сайта, а задание их прямо запрещает. Обе ниже.

## Замечено попутно

Ничего из этого не чинилось.

1. **`/license.txt` открыт наружу.** Отдаётся 200, 19 903 байта, заголовок
   `server: nginx-reuseport/1.21.1`. Это не «слетело правило в .htaccess»,
   как предполагает текст самого `monitor.sh`: nginx отдаёт статику мимо
   Apache, и `.htaccess` на `.txt` не действует вообще (то же сказано в
   инструкции, п. 3.7). `/readme.html` при этом закрыт — 403, его отдаёт
   Apache. Значит, закрыть `license.txt` можно только в панели хостинга;
   это работа владельца. Заодно стоит поправить и текст сообщения в
   `monitor.sh`, он уводит по ложному следу.

2. **У `/catalog/koltsa-kolodeznye-ks/ks-10-9/` в разметке нет цены.**
   Проверено по сырому HTML, не разбором графа. На странице три блока
   `"@type":"Product"` — `КС 10-5`, `КС 10-6`, `КС 10-10` — и ни у одного нет
   `offers`. Цена лежит только внутри `additionalProperty` («Цена с НДС, ₽»),
   а поисковику нужен `offers.price`. Для сравнения, соседняя проверяемая
   страница `/catalog/vodopropusknye-truby-zk/zk-3-200/` устроена правильно:
   один `Product`, внутри `offers` с `price: 15855` и `priceCurrency: RUB`.
   Отдельно странно, что на странице с адресом `ks-10-9` нет товара с именем
   `КС 10-9`. Похоже на осечку `rz-extract-products.php` на этой странице;
   сколько ещё страниц задето — не проверял, задания на обход не было.

3. **Числа из задания 002 устарели.** Там сказано «88 адресов карты сайта»
   (обход 03.09.2026). Сейчас в карте 226 адресов: `post-sitemap.xml` — 23,
   `page-sitemap1.xml` — 200, `page-sitemap2.xml` — 3. Опубликованных
   страниц в базе 204. Значит, оценки «блок на 21 странице» и «37 пустых
   заглушек на 18 страницах» покрывают меньше половины сайта, и пакет
   замены, собранный по ним, может пройти мимо части страниц. Стоит
   пересчитать до сборки пакета.

## Откат

Всё сделанное на сервере снимается тремя командами:

```
crontab -r                                  # снять расписание
rm -rf /srv/regiongbi/bin /srv/regiongbi/config.env /srv/regiongbi/crontab.zhbi
rm -rf /srv/regiongbi/backups/2026-09-04    # если бэкап не нужен
```

Правки в репозитории (`outbox/`, `done/`, `state/site.json`) откатываются
`git revert` соответствующего коммита.

Сайт не менялся: за всё задание к Бегету шли только чтение и `wp db export`
во временный файл, который скрипт после переноса удалил. Откатывать на
стороне сайта нечего. Бэкап на случай, если понадобится:
`/srv/regiongbi/backups/2026-09-04/db-20260904-2106.sql.zst`, разворачивается
`zstd -d db-20260904-2106.sql.zst` и `wp db import`.
